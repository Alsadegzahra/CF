# CourtFlow — System Architecture

## Overview

CourtFlow is a post-match analytics platform for padel. It has three layers:

1. **Edge / local** — video capture and pipeline processing (runs on a laptop or Raspberry Pi)
2. **Cloud** — artifact storage (Cloudflare R2) and API hosting (Render)
3. **Client** — React web dashboard served from the API

---

## System Components

### 1. Video Ingestion (`src/video/`)
Accepts a raw `.mp4` match file. Uses FFmpeg/ffprobe to validate the file, extract metadata (duration, FPS, resolution), and write a normalised copy for the pipeline. Entry point: `src/video/ingest.py`.

### 2. Court Calibration (`src/court/`)
A one-time setup per court. Uses OpenCV to compute a homography matrix that maps image pixel coordinates to normalised court space (0–1 on a 10 m × 20 m padel court). Calibration artifacts (homography matrix, ROI polygon, reference frame) are stored under `data/courts/<court_id>/calibration/`. Entry: `src/court/calibration/homography.py`.

### 3. Vision Pipeline (`src/vision/`)
Runs on every match after ingestion.

| Sub-component | File | Role |
|---|---|---|
| Person detection | `detection/yolo.py` | YOLOv8 / custom `best.pt` — bounding boxes per frame |
| ROI filter | `roi_filter/filter.py` | Removes detections outside the court polygon |
| Multi-object tracking | `tracking/mot.py` | ByteTrack / BoT-SORT — stable player IDs across frames |
| Canonical ID assignment | `tracking/canonical_ids.py` | Maps tracker IDs to fixed roles P1–P4 |
| Ground point estimation | `tracking/ground_point.py` | Foot-point from bounding box |
| Court coordinate mapping | `mapping/img_to_court.py` | Applies homography to get `(x_court, y_court)` |

Output: a `tracks.db` SQLite table of `(frame, player_id, x_pixel, y_pixel, x_court, y_court, timestamp)`.

### 4. Analytics Engine (`src/analytics/`)
Three tiers, each consuming the track records:

| Tier | File | Metrics |
|---|---|---|
| T1 — Movement basics | `tier1.py` | Distance (m), active duration, distance rank & share |
| T2 — Physical load | `tier2.py` | Avg/max speed (m/s), sprint count (>4 m/s), heatmap references |
| T3 — Spatial & dynamics | `tier3.py` | 6-zone coverage, net/baseline %, lateral %, accel/decel counts, team spacing, intensity windows |

Heatmap PNGs are generated by `analytics/heatmap.py` using kernel density over court coordinates.

### 5. Report Assembly (`src/analytics/report.py`, `report_pdf.py`)
Combines T1/T2/T3 outputs and match metadata into:
- `report.json` — structured JSON consumed by the dashboard
- `report.pdf` — formatted PDF for sharing/printing

### 6. Highlight Generation (`src/highlights/`)
- `select.py` — identifies high-intensity time windows from the movement intensity timeline
- `export.py` — calls FFmpeg to cut and render MP4 clips; assembles a highlight reel

### 7. API (`src/app/api.py`)
FastAPI application that:
- Serves match list, report JSON, heatmap images, and highlight video URLs
- Serves the built React dashboard (`dashboard/web/dist/`) at `/app`
- Proxies cloud-hosted artifacts via Cloudflare R2 presigned URLs when no local data exists

### 8. Cloud Storage (`src/cloud/`)
After processing, `upload.py` pushes artifacts to Cloudflare R2 (S3-compatible). The Render-hosted API reads from R2 when `data/matches/` is not present locally.

### 9. Dashboard (`dashboard/web/`)
React + Vite SPA. Three tabs:
- **Summary** — match overview, all-player performance grid, key insights
- **Analysis** — per-player physical metrics, positional charts, zone map, intensity timeline
- **Replay** — video player with track overlay

Supports English and Arabic (`src/i18n/strings.ts`). Auth and social features (saved matches, friends, feed) via Supabase.

## Data Flow

```
Video file
    │
    ▼
Ingest (FFmpeg)
    │  match.mp4
    ▼
Court Validation  ←── Calibration artifacts (homography.json, roi_polygon.json)
    │  validated court model
    ▼
YOLO Detection  →  ROI Filter  →  ByteTrack  →  Canonical IDs
    │  tracks.db (pixel coords)
    ▼
Homography Mapping
    │  tracks.db (court coords)
    ▼
Analytics (T1 + T2 + T3)  →  Heatmap generation
    │  movement metrics + heatmap PNGs
    ▼
Report Assembly  →  report.json + report.pdf
    │
    ▼
Highlight Selection  →  FFmpeg clip rendering  →  highlight_reel.mp4
    │
    ▼
Cloud Upload (Cloudflare R2)
    │  presigned URLs
    ▼
FastAPI  →  React Dashboard
```

---

## Pipeline Orchestration

The pipeline is managed by `src/pipeline/match_runner.py`, which calls numbered stages defined in `src/pipeline/stages.py`:

| Stage | Name |
|---|---|
| 00 | Validate court calibration |
| 01 | Ingest video |
| 02 | YOLO detection + tracking |
| 03 | Coordinate mapping |
| 04 | Analytics computation |
| 05 | Report + heatmap generation |
| 06 | Highlight selection + export |
| 07 | (Optional) Cloud upload |

Match state (PENDING → PROCESSING → DONE / FAILED) is tracked in `data/courtflow.db` (SQLite).

## Deployment Architecture

```
Local machine                   Render (cloud)
─────────────────               ──────────────────────────
run-match CLI                   FastAPI + React dashboard
     │                                │
     │  upload artifacts              │  reads via presigned URLs
     └──────────────────► Cloudflare R2 ◄────────────────────┘
                          (report.json, heatmaps,
                           highlight clips)
```

Supabase handles user authentication and social data (saved matches, friend connections) independently of the analytics pipeline.
